作为辅助诊断，仅在q2非空的同一40条报告上，q0的MAP为0.5209，q2为0.4637；下降并不完全由4个空行为查询造成。主结果仍使用全部44条，不按查询是否为空筛选评价样本。

**当前摘录与等权融合方案仍未提升总体效果。原文两路RRF在这组报告上有收益，因此不能把先前Requests上的融合退化推广成“RRF普遍无效”。**

### 新组互补性

- q2补救3条原文AST96未首位命中的报告，但损失7条原首位命中；Top-10补救0条、损失10条。
- q1或q2任一路命中，合计补救6条原AST96的首位未命中；仍没有补救其Top-10漏报。此处是命中事件取“或”，不是固定K预算的融合排名。
- 相对两种原文检索的首位命中并集，新增3条首位命中：Seaborn #2946、#3180，Flask #4935。相对两种原文检索没有新增Top-5或Top-10报告级覆盖。
- 事后用标签挑选AP最高的整条排名时，q0/q1/q2选择上限为0.6253，低于仅两种原文通道的选择上限0.6303；将增强通道加入两种原文通道后，上限为0.6849。上限不等于可实现的选择器成绩，也不代表可从查询特征预测应选择哪一路。

这组仍存在部分头部排序互补，但没有新增报告覆盖。结合Requests结果，不应把当前固定摘录加等权RRF作为已有效的模块；若后续研究选择器，应优先比较无需LLM的原文两路选择对照，并使用独立开发集。

## 复现

环境与LLM启动沿用 [两阶段运行说明](report-multiview.md#运行先生成释放显存再检索)。从项目根目录执行：

```bash
python -B -u scripts/retrieval/run_multiview.py --config configs/experiments/report_multiview_crossproject.json --prepare
# 停止本次生成服务释放显存，并启动既有 Elasticsearch
python -B -u scripts/retrieval/run_multiview.py --config configs/experiments/report_multiview_crossproject.json --run
```

若携带本机保存的选择清单，在以上两条命令均追加：

```text
--selection results/multiview/selections/crossproject_44_20261026/selection.json
```

生成缓存、模型、快照和结果不随Git上传。换设备运行时记录新的推理版本与环境；不要把Windows的推理程序或Python环境直接复制到Ubuntu。

完成后复核：

```bash
python -B scripts/analysis/analyze_multiview.py results/multiview/20261026_065207_539604_retrieval
python -B scripts/analysis/analyze_query_complementarity.py results/multiview/20261026_065207_539604_retrieval
```

`project_summary.json` 按项目保存六条路线的指标；`verification.json` 校验查询证据、融合及指标；`complementarity.json` 和对应CSV记录补救/损失与理想选择上限。新组没有历史AST排名作为外部对照，因此审计不声称已经验证历史排名一致。

本次样本数量较小且按原始顺序选取；这是固定方案的跨项目探索性复核，不是整个数据集的正式基准成绩。不能直接用新组的绝对指标高低与Requests比较难度，应比较同一组报告内各路线的配对差异。
