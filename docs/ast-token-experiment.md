# AST token 预算与动态规划：候选改进模块

本轮结论：两条新路线均未超过原 AST，当前保留为实验性路线，不替换默认方法，也不作为已成立的论文创新点。完整 44 条报告、四条路线全部成功；下方记录负结果及可验证的后续方向。

## 实验前冻结的方案（2026-10-25）

动机：现有 AST 路线先按 1500 字符递归装箱，再按 tokenizer 限长。现有 44 条报告中 61,902 个 AST 块有 26,563 个二次拆分，9,378 个总长度小于 128 tokens。动态路线对应数字为 56,325 / 26,954 / 2,797。这是描述性诊断，不是检索损失的因果证据。

新增两路，不替换四路基线：

- `ast_token_greedy`：以真实 tokenizer + 当前块真实结构前缀的总长度判断 AST 子树是否能完整保留；超长节点递归，最后将可容纳的相邻单元贪心合并。
- `ast_token_dp`：使用同一套 AST 原子单元，以动态规划选择切点，减少深层结构切断、跨方法混合与不充分利用预算。

共同约束：同一模型、512 总 tokens、64 前缀 tokens、原始源码按字节完整且不重叠覆盖；遇到超长不可再拆 AST 叶节点才按 token 安全边界兜底。块数不固定，需同时报告成本。两路均只使用修复前源码，不访问 Bug Report 或真实缺陷标签。

DP 对每条候选块边的代价为：

`1 + 0.25 × min(末端原子深度, 8) + 0.5 × max(方法签名数 - 1, 0) + 0.2 × (1 - 实际总tokens / 512)²`

文件末端不计切点深度代价。候选边最多跨 32 个相邻原子单元；动态规划只对这个有界候选图求全局最优，不声称无限候选下的最优。贪心消融使用相同候选窗口。实际前缀和 token 长度逐块精确测量，不依赖 token 数随拼接严格单调的假设。所有常数在读取新增路线的指标前冻结，本轮不按结果调参。

## 对比与解释规则

1. 同一次运行，对已有完整 44 条 requests 清单运行 `dynamic`、`blagent_ast`、`ast_token_greedy`、`ast_token_dp`。
2. 固定 Max 为主要比较聚合；Top-3 Mean 和归一化 LogSumExp 由原流程同时输出，只作为次要分析，不从中挑最高值替换主结论。
3. 主要指标 MAP@10；报告 MRR@10、Top-1/5/10、MeanRecall@10、逐样本胜/平/负、配对 bootstrap 区间、切块数、token 分布、时间与新增向量数。
4. 44 条同项目样本此前已被观察，是探索性比较，不是未接触的最终测试集。不根据本轮分数循环调权重；下一步必须在独立项目或预先固定验证集上验证。
5. 只有新方法优于 AST 主基线、并有跨项目和消融证据后，才能主张有效改进；不能只比动态块而回避更强 AST 基线。

## 新颖性边界

[cAST / EMNLP 2025](https://aclanthology.org/2025.findings-emnlp.430/) 已研究 AST 递归拆分、兄弟合并与结构元数据；本项目也已有 BLAZE 动态规划参考实现。因此“用了 AST / token / DP”本身不足以证明论文创新。本模块目前是结构与预算联合约束的工程原型，其代价函数与缺陷定位任务的适配价值，需要本轮及后续独立实验支持；不能直接写成已证明的新颖算法。

基础配置不修改，使用独立实验配置；旧模型编码器、AST/动态切块文件及其缓存指纹保持不变。相同结构作用域的前缀只计算一次：已对首次真实样本的 70 个文件、两条新路线核对完整 chunks/parents，对缓存优化前后的 140 份输出逐项比较，完全相同。这只是消除重复计算，不改变切点或代价函数。

## 复现

先按主 README 准备 Python、数据、模型及 ES，激活虚拟环境，在项目根目录执行。下列命令兼容 Windows / Ubuntu：

```bash
python -B -m unittest discover -s tests -q
# 首次单样本验证
python -B -u scripts/retrieval/run_vector_batch.py --config configs/experiments/ast_token_experiment.json --limit 1
# 固定配置：原数据顺序下前 44 条 psf/requests，无 RRF，主聚合 Max
python -B -u scripts/retrieval/run_vector_batch.py --config configs/experiments/ast_token_experiment.json
```

若已持有此前对比运行的 `selection.json`，推荐在最后一条命令加 `--selection <已有selection.json路径>`，程序会核对样本、查询、标签及数据集元数据的指纹。不要同时传 `--limit` 或 `--repository`。

运行完成后，将日志打印的批次目录传给分析脚本：

```bash
python -B scripts/analysis/analyze_chunking_experiment.py <本次批次目录>
# 可选：同时核对同一清单上两条旧路线的完整文件排名和指标
python -B scripts/analysis/analyze_chunking_experiment.py <本次批次目录> --reference <原44条语义批次目录>
# 小型多语言端到端验证；不是跨项目效果评测
python -B scripts/retrieval/verify_multilingual_ast.py
```

分析脚本要求全部样本成功、同一候选与标签、Max 主聚合且不融合；重新汇总逐报告指标后核对 `summary.json`，导出 `chunking_analysis.json` 和 `chunking_analysis.csv`。它不重新执行模型或检索。原始排名、各聚合结果、块内容与逐块分数仍由现有入口保存。

只有显式选用独立配置或 `--routes ast_token_greedy ast_token_dp --no-fusion` 才运行新方法。无需新增依赖。首次 DP 切块会较慢，大型数字表中的许多小节点可能触发 32 原子窗口上限；不能将缓存命中后的耗时当成冷启动成本。新路线的缓存和 ES 索引独立，旧四路保持原有行为。

### 切块与运行成本

下表块数是 44 个报告快照中的块实例总和，相同源码在多个报告中会重复计数。

| 路线 | 块实例数 | token 中位数 | 小于128 tokens | 达到32原子上限的块 | 本轮路线耗时 | 本轮新增向量 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| dynamic | 56,325 | 430 | 4.97% | — | 12.6 s | 0 |
| 原 AST | 61,902 | 374 | 15.15% | — | 14.0 s | 0 |
| token 贪心 | 113,627 | 186 | 31.00% | 99,922 | 624.1 s | 10,246 |
| token DP | 113,637 | 187 | 30.47% | 98,683 | 2,645.0 s | 8,565 |

旧路线已缓存，新路线混合了首次构建和复用；新向量数还受先运行贪心路线及单样本缓存的影响。这些耗时不是公平冷启动速度对比，新增向量数也不等于每种算法从零构建所需总量。即便如此，新方案约 1.84 倍的块实例数和首次 DP 切块成本，都是需要解决的实际问题。

### 结果诊断与适用边界

1. **候选窗口导致明显碎片化。** 贪心约 88%、DP 约 87% 的块达到 32 原子上限，而总长度中位数只有约 187 tokens。单样本中，大量这种块来自 `requests/packages/charade` 的数字表：数字各自成为小 AST 原子，窗口先于 token 预算耗尽。这是已观察到的切块问题；未做对应消融，不能把全部指标下降归因于此。
2. **结构代价更低并不等于定位更准。** DP 总代价从贪心的 240,237.95 降至 239,421.14，但 MAP@10 反而下降 0.0285。当前深度、跨方法与预算利用率代价，没有证明能代理缺陷定位相关性。
3. **实际排名存在明显退化。** #1962 的真实文件 `requests/sessions.py` 从原 AST 的第 1 名降至贪心第 4、DP 第 5；#6028 的 `requests/utils.py` 从第 1 降至第 5。也有改善：#1339 的两个真实文件由第 1/4 名变成第 1/2 名，AP 从 0.75 提升至 1。不能仅以少数改善样本概括整体效果。

后续值得验证的是：在开发集上先解决纯字面量数组的小原子合并与候选预算问题，再检验保留函数说明、语句边界及局部依赖上下文是否有用；保持原 AST 作为强基线，分别消融各项改动。应预先划定独立项目或验证集，冻结方法后再进行最终评测。本轮不继续用相同 44 条报告反复调权重，也不声称上述后续设想已有效。
