# 补全报告后的功能推测与 AST64 检索

本实验接受用户指定的流程：原报告 → OB／EB／S2R 补全 → 大模型推测可疑功能 → 推测内容与代码做语义检索。固定使用 Requests 44 条探索集和 AST64，不接入仓库知识库。

参考 [CosFL 论文 §3.2](https://arxiv.org/html/2411.17230v1#S3.SS2) 与官方 [Diagnose/prompt.py](https://github.com/IntHelloWorld/CosFL/blob/a3782298fae4ed24f80b2c7651aedff67198e00a/Diagnose/prompt.py)。CosFL 根据故障信息生成多粒度功能描述，在需要时请求模块知识；本轮只借鉴功能推测的思路，去掉模块知识请求。代码侧继续检索原始 AST64 代码块，不构造 CosFL 的多粒度知识摘要索引，因此不称为 CosFL 完整复现或其标准消融。

## 输入与生成

复用上一轮 `results/report_enrichment/20261109_152957_988093_retrieval/` 的原始报告和已校验 OB／EB／S2R，不重新生成第一阶段。第二阶段只传递 `original_report` 和 `OB_EB_S2R`，不传递源码、候选文件、标签、排名、评价指标或第一阶段未校验原始输出。通过白名单构造模型输入。

生成模型为本地 Qwen3-8B、BF16、greedy、关闭 thinking。输入上限 12000 tokens，超限报错；输出上限 1024 tokens。一次生成四项：

- `conflict`：实际和期望的差异，用于审计，不作为独立检索查询。
- `context`：可能出问题的概念性功能模块及职责。
- `functionality`：应该寻找的操作实现，描述输入、输出及条件。
- `logic`：可能解释异常的分支、状态变化、数据处理或组件交互。

这里明确允许功能与逻辑推测，不要求它们逐字出现在报告中，也不沿用上一轮的引文剔除规则。提示词要求不编造具体文件、类、方法名或行号，但这是提示词约束，不是已验证的事实保证。输出整体标为 speculative。结构错误或截断会保留第一次响应、将推测查询置空，原文和 OB／EB／S2R 对照继续参与评价。不因效果重试或筛选响应。

44 个样本中存在两个完全相同的正文，复用一次生成，仍保留全部 44 个评价样本。模型文件、提示词、输入和生成参数均参与缓存身份。

## 事前固定对比

代码侧：AST64（1500 字符预算、64 token 前缀、512 token 总输入），Qwen3-Embedding-0.6B，Max 文件聚合，精确语义检索，@10 评价。

10 个直接查询：原文、OB+EB+S2R、context、functionality、logic、context+functionality、functionality+logic、三项推测拼接、原文后追加推测、推测后追加原文。

12 组 RRF：原文权重固定 1，三项推测拼接的权重为 0.25／0.5／1／2，RRF 常数为 10／30／60。以上网格在检索前固定，来自上一轮相同网格。主问题是推测文本直接检索能否改善定位，融合结果作为辅助对比。

本机 GPU 0 正被其他服务使用，因此生成与检索均通过 `CUDA_VISIBLE_DEVICES=1` 在物理 GPU 1 执行。语义配置的 gpu_count 为 1；模型、精度和检索算法不变。重新运行原文与 OB／EB／S2R 对照，独立比较历史完整排名，检验设备数量变化是否影响对照。运行中发现单／双 GPU 编码的部分相近分数及排名存在差异，因此只将本批次内的配对对照用于方法比较，并显式记录历史排名与指标的差异。

## 运行与产物

默认使用一条命令自动完成生成、检索、审计和最终汇总；逐样本输出写入日志，终端只输出最终结果：

```bash
.venv/bin/python -B scripts/experiments/run_report_hypothesis.py --gpu 1
```

已运行中的批次可以使用 `--resume-retrieval <批次目录>` 接入自动审计与汇总，不重复生成或检索。最终机器可读汇总为批次中的 `final_summary.json`，阶段日志保存在 `results/report_hypothesis/automation/`。

以下是需要单独调试阶段时的入口：

```bash
CUDA_VISIBLE_DEVICES=1 .venv/bin/python -B -u scripts/retrieval/run_report_enrichment.py \
  --config configs/experiments/report_hypothesis_ast64.json --prepare
CUDA_VISIBLE_DEVICES=1 .venv/bin/python -B -u scripts/retrieval/run_report_enrichment.py \
  --config configs/experiments/report_hypothesis_ast64.json --run
.venv/bin/python -B scripts/analysis/analyze_report_hypothesis.py results/report_hypothesis/<检索批次>
```

生成缓存：`cache/report_hypothesis/`。批次：`results/report_hypothesis/`。每份产物记录首次原始输出、实际模型输入、补全来源哈希、推测内容、实际检索文本和输入截断。`comparison.csv` 保存参数对比，`verification.json` 重算指标和融合，`hypothesis_verification.json` 验证输入边界、样本对齐、原文及 OB／EB／S2R 两组历史完整排名和指标的一致／差异情况。

只在报告与已生成查询文件中读取生成输入；审计阶段才读取标签和排名核对结果，审计不反向更新提示词或生成缓存。

### 主要结论

功能推测明显优于只使用 OB／EB／S2R：三层推测拼接 MAP 为 0.6245，对照为 0.4443，提高 0.1801。三层推测的 MAP 略低于原文 0.6317，但 MRR、Top-1、Top-5、Top-10 均高于原文。直接推测 Top-1 为 23/44，原文为 21/44；Top-10 为 43/44，原文为 42/44。推测的 MeanRecall@10 为 0.9290，低于原文 0.9418，因此不能说所有指标都改善。

最佳融合为推测权重 0.25、常数 30 或 60，两组 MAP 均为 0.6457，比原文提高 0.0140（相对约 2.22%）。逐报告为 3 胜、40 平、1 负，增益主要来自 #3718；增加推测权重未继续带来收益。两种文本直接拼接均低于原文。

直接推测在 Top-10 补救 #2153、#2873，但丢失 #1724。最佳融合的 Top-10 覆盖与原文相同，未保留这两条补救的新增覆盖。这表明推测提供了互补信息，但当前简单融合不能同时获得所有收益。

本轮支持继续探索“功能假设 → 代码检索”，尤其是以小权重加入原文排名。它不是独立测试收益：44 条已用于探索，最佳参数仍需冻结后跨项目验证；没有运行“仅原报告直接生成同类假设”的消融，因此不能将收益单独归因于前置 OB／EB／S2R 补全。

### 与历史批次的数值差异

历史双 GPU 原文 MAP 为 0.6289，本次单 GPU 为 0.6317；OB／EB／S2R 从 0.4329 变为 0.4443。模型文件、编码实现、精度、查询文本、候选文件和代码块文本均已核对；编码身份仅 GPU 数量／设备列表不同。单／双 GPU 执行出现分数及排名差异，本轮所有方案均与本轮重跑的对照比较。

原文逐报告指标 40/44 与历史一致，差异报告为 #1776、#2617、#2674、#2678；OB／EB／S2R 为 43/44 一致，差异报告为 #3738。完整排名分别只有 1/44 和 6/44 一致，不能宣称历史排名复现。具体分数差异保存在 `hypothesis_verification.json`。
