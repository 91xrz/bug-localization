# 固定候选内的两步查证重排

只改 C 阶段，不为任何报告搜索新文件。借用 [BLAgent](https://arxiv.org/html/2605.17965v2) 的“先看结构，再看实现”和 [GenLoc](https://arxiv.org/html/2508.00253v3) 的“根据刚看到的代码决定下一步”。不是两个系统的复现或输出融合，不使用它们的预测指导推理。

## 冻结的方法

1. 复用原 C3 和普通 8B 的已有排名。两者首位相同时不调用 Agent，初排失败仍在完整分母中计零。首位不同时从原前十选三个既有文件：8B 首选、C3 首选和按 8B 顺序靠前的另一文件。
2. 只读取三份文件的修复前快照；核对源码哈希。给模型看每文件最多 12 项的结构菜单，含限定名、行范围、选项 ID，以及原来已有的短摘录。报告输入上限 2048 tokens。模型提出一个区分性问题，并在 8B 首选文件中选一个符号。
3. 根据选项 ID 读取真实代码，每份新增正文最多 384 tokens；只返回整行，显式标明是否完整。**顺序查证组**在看过第一段正文后，从另外两个文件中选择第二个符号；**无反馈对照组**在选择这一步只看到同样的菜单、原短摘录、问题与第一选择 ID，不看到第一段新正文。两个组最后都把实际选到的两段代码交给同一裁决提示，允许保留原排名或弃权。调用上限、证据上限相同，但实际输入 tokens 不强制相等。
4. 只能把第二个被检查文件提升到首位，其他相对次序不变。两臂输出的前十文件集合、尾部以及逐例输入由单独的分析程序复核。结构化 ID 防止引用到查证结果以外的行，但不证明模型选对了符号或给出了正确解释。

主队列为上一轮 Agent 用过的 90 条；另一批为项目此前使用过的 confirmation90。两者报告身份不重叠，均属历史开发数据。两个队列在开始前固定，同一配置，不在中途挑选方法或根据成绩换报告。比较全分母的 MAP@10、Top-1 找回/误改、按项目分层的配对 bootstrap 95% 区间以及相对普通 8B 的新增调用成本。对照组与顺序组各自的逻辑调用量均包含首次共享规划。

## 实测

| 方法 | 主 90：MAP@10 / Top-1 | 复核 90：MAP@10 / Top-1 |
|---|---:|---:|
| 普通 8B 联合重排 | 0.746384 / 64 | 0.780866 / 76 |
| 上轮单轮主动核查 | 0.753792 / 65 | 未运行 |
| 新两步、第二次选择不看第一段正文 | 0.739366 / 63 | 0.741977 / 69 |
| 新两步、第二次选择看第一段正文 | 0.744921 / 64 | 0.758644 / 72 |
| 同批本地 BLAgent 8B | 0.774953 / 69 | 0.715549 / 69 |

顺序查证相比无反馈的 ΔMAP 在主批为 +0.005556（95% 配对区间 [−0.011111,+0.022222]），复核批为 +0.016667（[0,+0.033333]）。相对普通 8B 则分别为 −0.001463 和 −0.022222。主批相对上一轮主动核查 −0.008870。第二批高于本地 BLAgent，但原 8B 起点本来就更高，不能归功于新增方法。

两批分别触发 36/38 次，均有 14 条在看到第一段正文后换了下一次读取的符号。顺序组相对普通重排的首位纠正/损失分别为 2/2、1/5。顺序组各需 108/114 次新增 8B 逻辑调用，输入 214,551/233,171 tokens。新实现真正改变了工具选择，但没带来端到端净收益。两批均验证前十集合与第十一名起的尾部不变；未接入默认流程。

Django #16333 的首次查证选对并完整读取了 `UserCreationForm.save`；两种选择策略的第二次读取却都是 `BaseModelFormSet.save.save_m2m`，顺序组最后弃权。不能把正确的原始排名计为新方法修正。后续可独立检验“保住首位，只重排第 2–5 名”，目标改为多文件 MAP，不声称提高 Top-1。
